# Linux application control surfaces for Adam

October 5, 2026 · Research and proposed experiments; no live applications were probed.

## Short answer

There is a useful route here, but no universal application socket. Browser protocols can expose a page's DOM and actions; Linux accessibility can expose many native controls; D-Bus and application APIs can expose exact state and operations. These surfaces differ by app, launch mode, task, and user permissions. Adam should discover **capabilities** and choose the narrowest source that can answer or perform the user's task, then verify the resulting state. It should keep screenshots and input automation for interfaces with no useful semantic route.

This is a survey of representative everyday Linux application families, not an exhaustive inventory of every program or an assertion that each installed app currently has an endpoint. A socket's existence alone is weak evidence: it may be private implementation IPC, require startup flags, or lack a supported control protocol.

## Browser map

| Browser family / examples | Supported route | How it becomes available | What it can do | Important limit |
| --- | --- | --- | --- | --- |
| Chromium: Chrome, Chromium, Edge, Brave, Vivaldi, Opera | [Chrome DevTools Protocol (CDP)](https://chromedevtools.github.io/devtools-protocol/) over a local WebSocket, with HTTP discovery endpoints; [Edge documents the same route](https://learn.microsoft.com/en-us/microsoft-edge/devtools/protocol/) | Browser launched with remote debugging or a controlled automation profile | Tabs, DOM, accessibility tree, network, page script, clicks, typing, navigation | Powerful access to the whole debugged profile; an ordinary browser session does not necessarily expose it. [Chrome 136 requires a nondefault user data directory](https://developer.chrome.com/blog/remote-debugging-port) for remote debugging switches. Chromium derivatives need per-build verification. |
| Firefox and Firefox derivatives, including Zen | [WebDriver BiDi and Marionette](https://firefox-source-docs.mozilla.org/remote/index.html); browser extension/native messaging is another route | Browser launched/configured for remote automation, or an installed permitted extension | Tabs, DOM, input, navigation, script, events | [Firefox CDP was removed in Firefox 141](https://firefox-source-docs.mozilla.org/remote/Prefs.html). [Playwright's Firefox requires its patched build](https://playwright.dev/docs/browsers/), so it is not a general attach route to the user's running Firefox. [Zen identifies itself as a Firefox fork](https://docs.zen-browser.app/contribute/desktop/code-structure-and-prefs). |
| GNOME Web/Epiphany and other WebKitGTK hosts | [WebKitGTK WebDriver automation](https://webkitgtk.org/reference/webkit2gtk/2.41.1/method.WebContext.set_automation_allowed.html) | Host explicitly enables automation | Web content navigation and interaction | Automation is disabled by default; embedding applications control whether the route exists. |
| qutebrowser | [Userscripts and command FIFO](https://qutebrowser.org/doc/userscripts.html); optional browser-engine automation if separately enabled | A userscript invocation / configured command channel | qutebrowser commands and task-specific extraction | Its FIFO is a qutebrowser interface, not a portable browser API. |
| Electron desktop apps, including some chat and editor apps | [Electron remote debugging switch](https://www.electronjs.org/docs/latest/api/command-line-switches) when exposed; app-specific extension/API where available | App launched with the switch or explicitly exposes an API | Inspect its renderer DOM and perhaps execute renderer actions | The renderer is only part of the app. CDP does not guarantee a stable product-level API, and many apps expose no debug endpoint by default. |

[WebDriver BiDi](https://www.w3.org/TR/webdriver-bidi/) is the standards route for bidirectional browser automation; it should be evaluated for Firefox rather than treating CDP as universal. CDP attachment through [Playwright `connectOverCDP`](https://playwright.dev/docs/api/class-browsertype) is Chromium only and has lower fidelity than Playwright's native protocol. Chrome's default-profile restriction also means “reuse my normal tab by opening a port” is no longer a reliable general design.

### A possible bridge to the user's existing browser

A small, explicitly installed WebExtension could read the active tab's permitted DOM and send bounded, task-specific observations to Adam via [Chrome native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) or [Firefox native messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging). The native messaging host uses JSON messages over standard input/output; it is not a public network socket. This could support Chromium and Firefox-derived browsers without a debug port. It still needs browser-specific packaging, extension and site permissions, frame handling, and a clear active-tab match. It cannot claim access to browser chrome, privileged pages, or sites where extension permissions do not apply. Compare it with an isolated automation profile before adopting it: the user may value continuity in the current tab, but an extension adds maintenance and permission burden.

For any browser route, distinguish the *web page* from browser UI (tabs, downloads, permissions) and native dialogs. DOM automation only covers the first reliably. AT-SPI and screenshots remain useful for the latter two.

## Linux desktop and everyday application map

| Application or task family | Useful exposed surface | Adam opportunity and limitation |
| --- | --- | --- |
| Desktop windows and controls across GTK, Qt, LibreOffice, etc. | [AT-SPI](https://gnome.pages.gitlab.gnome.org/at-spi2-core/libatspi/class.Accessible.html) over the accessibility bus: roles, names, actions, text, values, selections, tables | The broadest semantic fallback for native UI; coverage and labels vary by app. Adam already reads it. Use a fresh element identity before action, and confirm resulting state. |
| Launching/opening files in desktop apps | [D-Bus activatable desktop entries](https://xdg.pages.freedesktop.org/xdg-specs/desktop-entry/latest/dbus.html), with `Activate`, `Open`, and `ActivateAction` | Good for launch/open. Activation does not imply arbitrary inspection or manipulation of the app. |
| Media players: Spotify clients, VLC, Rhythmbox, etc. when supported | [MPRIS](https://specifications.freedesktop.org/mpris/latest/) D-Bus Player and metadata interfaces | Unified play/pause/skip/seek and current track/status for conforming players. Check for an actual `org.mpris.MediaPlayer2.*` service at runtime; app support differs. |
| Files and file managers: Nautilus, Dolphin, Thunar, Nemo | Filesystem/GIO APIs for file data and operations; [`org.freedesktop.FileManager1`](https://wiki.freedesktop.org/www/Specifications/) for showing files/folders if implemented; AT-SPI for UI | Work on files through the filesystem when appropriate. FileManager1 is for reveal/select, not a universal browse/copy/rename RPC. Treat Trash, mounts, and remote locations as separate capabilities. |
| Office: LibreOffice Writer, Calc, Impress | [UNO API](https://api.libreoffice.org/) with an explicitly enabled [socket or pipe bridge](https://docs.libreoffice.org/binaryurp.html) | Strong typed document model: paragraphs, cells, sheets, formatting, save/export. This is much more precise than clicking ribbon controls. Listener availability must be established; do not assume a running GUI instance is listening. |
| Email and calendar: Thunderbird, Evolution, GNOME Calendar | [Thunderbird MailExtensions](https://developer.thunderbird.net/add-ons/mailextensions/supported-webextension-api); [Evolution Data Server calendar API](https://gnome.pages.gitlab.gnome.org/evolution-data-server/libecal/class.Client.html); account protocol/service APIs | Can inspect or prepare structured messages/events in supported installations. A Thunderbird extension is installed code with mailbox permissions; EDS only applies to configured EDS accounts. Sending mail or invitations remains a consequential action. |
| Editors/IDEs: VS Code, VSCodium | [VS Code CLI](https://code.visualstudio.com/docs/configure/command-line) for open/diff/goto; [extension API](https://code.visualstudio.com/api/extension-guides/command) for editor/document state and commands | CLI can target files but is not a full editor state API. A local extension can be much richer, with version/permission upkeep. Use files directly for code edits when the user asks to change code. |
| Editors: Neovim, Emacs | [Neovim MessagePack-RPC](https://neovim.io/doc/user/api/) via local socket; [Emacs server/emacsclient](https://www.gnu.org/software/emacs/manual/html_node/emacs/Emacs-Server.html) | Near-complete buffer/window commands for an explicitly running server. Avoid arbitrary Lisp evaluation or open TCP listeners as a generic agent pathway. |
| Terminals: tmux and kitty | [tmux control mode](https://github.com/tmux/tmux/wiki/Control-Mode) and capture-pane; [kitty remote control](https://sw.kovidgoyal.net/kitty/remote-control/) when enabled | Reliable pane text and structured commands in those terminals. Ordinary terminal emulators do not share a universal scrollback API; AT-SPI is fallback. Adam already reads tmux and accessibility text. |
| OBS Studio | [Built-in WebSocket control](https://obsproject.com/kb/remote-control-guide), included since OBS 28 | Scene/source/output state and commands. A high-value first app adapter because a returned request can be verified from OBS state. Requires configured endpoint and authentication. |
| Local video players such as mpv | [mpv JSON IPC](https://mpv.io/manual/stable/) when started with `--input-ipc-server`; MPRIS when supported | Exact playback, tracks, time position and property observation. Per-app socket is opt-in. |
| Image editors such as GIMP | [GIMP Script-Fu](https://docs.gimp.org/3.0/en/gimp-filters-script-fu.html), file format APIs, AT-SPI | Scripts are good for known image transformations; no general assumption of a live external RPC socket. Visual UI still matters for selections/canvas intent. |
| PDFs and document viewers | Document text/layout extraction (for example [Poppler `pdftotext`](https://manpages.debian.org/unstable/poppler-utils/pdftotext.1.en.html)); AT-SPI for viewer controls | Read and search the source document directly when accessible. Page rendering is needed for diagrams, scans, or layout questions. A viewer's process socket is usually irrelevant. |
| System services and settings | [NetworkManager D-Bus](https://networkmanager.dev/docs/developers/), [WirePlumber `wpctl`](https://pipewire.pages.freedesktop.org/wireplumber/man/wpctl.html), Bluetooth BlueZ D-Bus, desktop-specific settings APIs | Prefer typed state for Wi-Fi/audio/device tasks and verify after change. Map each setting to its owner; there is no one “Linux settings” API. |
| Window manager, capture, input | [Hyprland IPC](https://wiki.hypr.land/IPC/) on Hyprland; [KWin scripting](https://develop.kde.org/docs/plasma/kwin/api/) on KDE; [XDG RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) for permissioned capture/input | Window metadata and compositor actions are desktop-specific. The portal requires user permission and supplies generic desktop control, not app semantics. |
| Chat apps, password managers, games, arbitrary custom UI | Often no documented local semantic control endpoint; service APIs, browser page DOM, AT-SPI, or screenshot/input may be available | Do not treat a process's private D-Bus name, Electron renderer, or Unix socket as a supported app API. Game UI and canvas-heavy apps usually need visual grounding unless a documented mod/API exists. Credential entry stays with the user. |

This map separates **app data** (for example a document or calendar entry) from **visible app state** (current tab, selection, dialog). A filesystem or service API may answer a question accurately without controlling the window; the visible UI may still require an accessibility or visual route. The task determines which is relevant.

## What Adam has now

Code inspection on this commit shows:

1. [`observe_desktop.py`](../src/tools/observe_desktop.py) identifies the focused Hyprland window (X11 fallback), reads AT-SPI, optionally captures a screenshot, and tries read-only CDP for six Chromium-name patterns. CDP is used only when `ADAM_CDP_ENDPOINT` is set or the active browser process advertises a loopback debugging port; it does not scan ports. It chooses a page by matching the window title and returns up to 3,500 body-text characters. This is useful evidence but can match the wrong tab when titles are duplicated, and it omits structured links/controls, iframe content, and provenance finer than “CDP”.
2. [`browser_navigation.py`](../src/tools/browser_navigation.py) launches a separate, lazy Playwright persistent profile. It can inspect pages, navigate, click links, fill fields, and scroll. It is not attached to the user's normal profile. Its bounded snapshot includes 6,000 body-text characters, up to 60 links, and up to 30 fields; references are tied to a page URL and element attributes. This gives a controlled browser path but has browser startup and process-memory cost.
3. The browser engine selector places `zen` in its Chromium list and tries to launch the Zen executable through `playwright.chromium`. Zen is a Firefox fork, so this branch is likely wrong and should be corrected before claiming Zen support. Playwright's patched-Firefox requirement means simply changing the string to `firefox` may still not support the installed Zen executable.
4. [`terminal_text.py`](../src/tools/terminal_text.py) already reads focused tmux text or accessibility text. Desktop tools already include compositor-specific routes. The next gain is therefore a capability-selection and verification layer, not a second generic screenshot tool.

The previous synthetic report result in the [desktop handoff](desktop-handoff-2026-10-05.md) is relevant: DOM text answered 3/3 dense-table questions where screenshot-only answered 0/3, with 7–11 ms extraction, but the isolated Edge browser cost about 577 MiB PSS while open. That result supports using a live semantic route when available, and keeping browser processes lazy and short-lived when launched solely for a task. Three synthetic trials do not establish broad accuracy.

## Proposed architecture: a capability broker

Adam should resolve each request to an **object and operation**, not just an app name. For example, “read the total in this web report” targets page content; “change the active OBS scene” targets OBS's scene state; “click Allow in this permission dialog” targets browser chrome/native UI. The broker receives focused window/PID, desktop session, task, and any user-selected file/account, then asks small adapters whether they can read or act.

Each adapter should report: capability (`read_page`, `set_scene`, `read_buffer`, etc.), scope (window/tab/document/session), availability reason, whether it can mutate, freshness, resource cost, and a verification method. Discovery should use known service names, process metadata, advertised endpoints, or an installed extension—**not** arbitrary local port/socket scanning. Rank candidates by task fit and expected evidence quality. A typical order is typed app API or source document, browser DOM/BiDi where the page is the object, AT-SPI for native controls, then screenshot/OCR/vision for visual or unsupported UI. More than one source can be combined: a screenshot can identify the target, while an API confirms the final value.

The broker should keep a small result record: target identity, surface used, observation timestamp, action, post-action state, and uncertainty. It must distinguish “command accepted” from “goal achieved”. For example, after `SetCurrentProgramScene`, read the current scene; after editing a Calc cell, read that cell from UNO; after clicking a browser link, confirm URL and relevant page state. This avoids success claims based on a tool call alone.

Memory constraints argue for **lazy adapters**. A D-Bus query, existing tmux socket, or already-enabled browser endpoint is cheap to try. A fresh browser or vision worker is comparatively expensive; start only for a task that benefits from it, then release it. Record process-tree PSS/RSS and startup time per adapter on the same host before choosing a default.

## Concrete exploration sequence

1. **Read-only capability census on an authorized host.** For currently installed, user-approved apps, record desktop ID, version, accessibility coverage, documented D-Bus names, advertised local endpoints, and whether activation is needed. Do not infer API support from open sockets. No Desky probes while its pause in the handoff remains in force.
2. **Browser comparison on a synthetic local page.** On an isolated profile, compare Chromium CDP, Firefox WebDriver BiDi, and a permitted extension/native-messaging prototype. Try WebKitGTK WebDriver only if an appropriate opt-in host is available. Measure tab matching, dynamic content, iframes, labeled controls, action verification, cold/warm latency, and incremental PSS. Keep the existing screenshot/AT-SPI baseline on the same fixture.
3. **One typed app adapter.** OBS WebSocket is a good first candidate if OBS is actually installed and used: query current scene, change to a synthetic/test scene, and query again. LibreOffice UNO is another strong candidate for document tasks, but needs a controlled listener. Prefer the app that maps to real user tasks.
4. **Implement the broker after the measurements.** Start with read-only capability reports and one or two adapters. Preserve the generic desktop route for unsupported cases and mixed requests. Use feature gates so an unavailable app API never blocks a normal task.
5. **Evaluate whole tasks, not only extraction speed.** Record correct target, successful action, verified outcome, false-success rate, fallback rate, model/tool turns, first meaningful acknowledgment, p50/p95 total time, CPU, and incremental memory. Use the same initial state and prompt for each route; small samples are exploratory.

The most promising immediate change is richer, more reliable browser observation from an **already authorized** session, followed by OBS or LibreOffice task APIs. Generic socket enumeration is unlikely to yield a portable computer-use layer because most visible sockets are private IPC and lack stable object semantics.

## Boundary conditions

Remote browser control can read session data and execute page script; [Firefox documents the remote agent's security implications](https://firefox-source-docs.mozilla.org/remote/Security.html). Restrict debug endpoints to local scope and controlled profiles, and expose only bounded task-relevant observations to the model. Do not derive an endpoint from untrusted page content. Extension/native-messaging and portal paths require explicit setup and permissions. These are design constraints for a dependable interface, not reasons to avoid the research.

Application versions and desktop environments will keep changing. The broker should treat each adapter as an optional capability with runtime detection and a generic fallback, and its documentation should distinguish official stable APIs from inferred implementation details.
